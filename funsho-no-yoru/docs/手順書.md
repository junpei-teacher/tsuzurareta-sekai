# 『焚書の夜』実装手順書

設計書（`docs/設計書.md`）に基づく実装手順。**上から順に実行する。**

## 進め方の原則

1. **1フェーズ＝1コミット。** フェーズの完了条件を満たさないまま次へ進まない
2. **仕様を変えるときは、コードより先に設計書を書き換える**
3. **各フェーズは必ず「ブラウザで動かして確認」で終わる。** 動かないコードを積み上げない
4. アセット（ドット絵・立ち絵）の投入は Phase 7。**それまでは全部色付きの矩形で作る**
   — 素材待ちで実装が止まるのが、この手の企画が死ぬ最大の原因

# Phase 0 — 環境構築と土台

## 0-1. プロジェクト作成

```bash
cd C:/programming/game && npm create vite@latest . -- --template vanilla-ts
```

```bash
npm install
```

## 0-2. バージョン管理

```bash
git init && git add -A && git commit -m "chore: Vite + TypeScript 初期化"
```

## 0-3. ディレクトリを設計書 7.6 の構成に合わせる

`src/core` `src/spell` `src/scenes` `src/ui` `data` `tools` `public/assets` を作成する。

## 0-4. 描画基盤

- `<canvas>` を内部解像度 **480 × 270** で作る
- ウィンドウサイズから**整数倍のスケール値**を計算し、CSS で拡大する
- `ctx.imageSmoothingEnabled = false`
- `requestAnimationFrame` のゲームループ（update / render 分離）
- キー入力を1箇所で受けるマネージャ（`keydown` / `keyup` を配列で保持）

## 0-5. 日本語ドットフォント

**PixelMplus12** を `public/assets/fonts/` に配置し、`@font-face` で読み込む。
**ライセンス条件を必ず読んでから使う。**

## 0-6. フリー素材の選定（重要）

書庫内装のタイルセットと、16px キャラチップを**同一の配布元から**確保する。
配布元が混ざると画面が寄せ集めに見える。候補を調べたら、
`docs/assets-license.md` に URL・作者・ライセンス条文を記録すること。

必要なもの：
- 石造りの屋内タイルセット（床・壁・階段・扉）
- 本棚・机・燭台などの小物
- 人物キャラチップ（4方向 × 3フレーム）を最低3体分

## 完了条件

黒い画面に「あいうえお」がドットフォントで表示され、矢印キーで白い矩形が動く。

# Phase 1 — 詠唱エンジン（★最重要・凍結対象）

**このフェーズが本作の心臓部。ここが面白くなければ企画ごと考え直す。**

## 1-1. ハッシュ関数

`src/spell/hash.ts` に設計書 3.3 の `spellHash` をそのまま実装する。

## 1-2. 帯判定

`src/spell/resolver.ts` に設計書 3.4 のテーブルを実装する。

```ts
resolveSpell(input: string): { tier, index } | "DUD"
```

## 1-3. 分布の検証（必須）

ランダムな文字列を **10万回**流し込み、実際の出現率が設計値
（不発10% / コモン47% / アンコモン27% / レア13% / **神話3%**）に
**±1%以内**で一致することを確認する。ズレる場合は帯の境界値を調整する。

さらに、**帯内の個体分布が偏っていないこと**も確認する
（`q % 帯サイズ` が特定の値に集中していないか）。

## 1-4. 詠唱テストベッド

画面に入力欄だけを出し、文字列を打ってEnterを押すと
「どの帯の何番が出たか」がテキストで表示されるだけの画面を作る。

## 1-5. 【重要】ハッシュ関数を凍結する

分布の検証が通ったら、`hash.ts` の先頭に以下を書き込む。

```ts
// ============================================================
// 【凍結】この関数を変更してはならない。
// 巻物の呪文名は、この関数からの逆引きで決定されている。
// 1文字でも変更すると全呪文名が別物になり、
// シナリオ・巻物・会話テキストが全て壊れる。
// ============================================================
```

## 完了条件

テストベッドで100回ほど手打ちして、**「もう1回打ちたい」と思えること。**
思えなければ、帯の確率か演出を調整する。ここで妥協しない。

# Phase 2 — 呪文名の逆引き（spell-forge）

## 2-1. 呪文テーブルの骨格を作る

`data/spells.json` に57種の枠を作る。この時点では効果パラメータだけ埋め、
`canonical`（呪文文字列）は空にしておく。

配分：コモン20 / アンコモン20 / レア12 / 神話5。
うち **12〜15種を「巻物呪文」**として印を付け、専用エフェクトとフレーバーを与える。

**ミラがくれる最初の呪文はアンコモン帯に置く**（設計書 3.4.1）。これが乱打の基準線になる。

**コモン20種は「弱い呪文」にしない**（設計書 3.4.2）。MP 3〜6の安さ、弱点特化、
状態異常など、火力以外の役割を必ず持たせる。ここが単なる下位互換だと、
賭けの47%がハズレになって不発率を下げた意味が消える。

## 2-2. 候補文字列の自動生成

`tools/spell-forge.ts` を作る。

1. 子音・母音のパターンから**発音しやすい文字列**を10万個生成する
   （例：`CVCCVC` `CVCVC` `CVCCVCC` の型に子音・母音を流し込む）
2. 全部 `spellHash` に通して帯と個体を求める
3. 呪文IDごとに、当たった候補をリストアップして出力する

```bash
npx tsx tools/spell-forge.ts > tools/candidates.txt
```

## 2-3. 人間が選ぶ

各巻物呪文について、候補の中から**響きのいいものを選んで** `canonical` に書き込む。

選定基準：
- 4〜8文字。長すぎると戦闘中に打つのが苦痛
- 打鍵しやすい（同じ指の連打を避ける）
- 属性の印象と音が合う（炎なら破裂音、癒しなら流音、など）

## 2-4. 固有名詞もここで決める

同じ手順で、**禁書に書き込む固有名詞**を確定させる。

- 焚書を指揮する者の名前（4〜8文字英字）
- 隠し要素「読めない一語」
- ミラ `MIRA`（確定済み）

## 完了条件

`data/spells.json` の巻物呪文15種すべてに `canonical` が入り、
テストベッドでその文字列を打つと**狙った呪文が出る**。

# Phase 3 — 戦闘シーン

## 3-1. 戦闘ステートマシン

```
コマンド選択（詠唱 / 道具 / 逃げる）
  → 詠唱入力（時間制限なし）
  → 判定・演出
  → 敵行動
  → 勝敗判定
```

## 3-2. 詠唱入力UI（`src/ui/caster.ts`）

- DOM の `<input>` は使わない。`keydown` を直接拾ってCanvasに描く
- **前方一致サジェスト**（設計書 3.2）。呪文帳の登録済み呪文のみ対象
- Tab / ↓ で候補確定、Enter で詠唱
- 半角英数字以外は受け付けない

## 3-3. ダメージ計算と属性

設計書 4.4 の式をそのまま実装する。弱点 ×2.0 / 耐性 ×0.5 / 無効 ×0。

## 3-4. 演出

この時点では**全部矩形とテキストでよい**。
- 攻撃：画面を短く赤くフラッシュ、敵矩形を揺らす
- 不発：`言葉は、意味をなさなかった。`
- **神話級：画面暗転 → 文字が一字ずつ浮かび上がる → 全画面フラッシュ**

## 3-5. MP不足の分岐（★目玉）

神話級を引いたがMPが足りない場合、設計書 3.6 の専用演出を出す。
**呪文帳には「未詠唱」として記録する。** 撃てなかったことを記憶させる。

## 完了条件

矩形の敵1体と最後まで戦えて、勝てる。負けるとゲームオーバーになる。

**乱打の手触りを必ず確認する。** 「打ってみてもいいか」と思えて、
かつ「毎ターン打つのは損だ」とも感じられる——この両立が成立していれば正解。
どちらかに振り切れている場合は帯の境界値かMPコストを調整する。

# Phase 7 — アセット投入

## 7-1. マップチップ・キャラチップ差し替え

Phase 0 で選定した素材を投入し、矩形を置き換える。

## 7-1.5 PixelLab（MCP）を1キャラで検証する

**このフェーズで最初にやること。** 設計書 8.1 の4項目を確かめる。
特に「4方向×3フレームの歩行アニメで同一人物に見えるか」。
ここが通れば、以下の 7-2 / 7-3 の手順は PixelLab に置き換えられる。
通らなければ、当初どおり立ち絵と敵のみAI生成、マップ上キャラはフリー素材にする。

## 7-2. 立ち絵のAI生成（6〜8人）

**一貫性を出すための手順：**

1. **プロンプトの骨格を固定する。** 変えるのはキャラ固有の記述だけ

```
pixel art portrait, 96x96, limited palette of 16 colors,
dark stone library interior background, candlelight from the left,
front-facing bust shot, muted earth tones with warm highlights,
clean hard pixel edges, no anti-aliasing, no text
--- character ---
[ここだけ差し替え：a young library apprentice, dusty grey robe, ...]
```

2. **同じシード値を使う**（対応するツールの場合）
3. **必ず後処理する。** 生成物はそのままでは「ドット風のぼやけた画像」であり、
   ドット絵ではない
   - GIMP または Aseprite で **16色にインデックスカラー化**
   - 96×96 などのグリッドに**ニアレストネイバーで縮小**
   - **全キャラで同一のパレットを使う**（これを怠ると人物ごとに色調がバラつく）
4. 目・口など顔の要点だけ手で打ち直す

**1キャラあたり1〜2時間を見込む。** 8人で丸2日。ここは削れない。

## 7-3. 敵グラフィック（8体・完了）

**`create_character` ではなく `create_image_pro` の正面1枚絵で作る。**
理由と、`glow`・呼吸の上下動・被弾シルエットの仕様は設計書 8.4 を見ること。

手順：

1. `create_image_pro` を8体ぶん**まとめて投げる**（非同期。並べて投げれば待ち時間は1回ぶん）
   - `width`/`height` は**170以下**。超えると候補が1枚になり選べなくなる
   - `no_background: true`
2. `get_image(job_id)` で候補を見て、1枚選ぶ
3. `npm run fetch -- public/assets/enemies "<download URL>" 1 --prefix <敵のid>`
4. `src/core/assets.ts` の `enemySprites(...)` に id を足す
5. `data/enemies.json` の `sprite.w/h` を実寸（実ピクセルの半分）に直す。
   火を持つ敵には `glow` を足す

**確認は1体ずつブラウザで見るより、8体を並べた1枚を作るほうが速い。**
足元を揃えて戦闘画面と同じ背景色に並べると、
大きさの序列と「背景に沈む敵」が一目で分かる。

## 7-3.5 立ち絵（6人・完了）

`create_portrait_character` は**テキストからは作れない**。既存のキャラ画像を
バストに変換するツールなので、**先に素体（フィールド用のドット絵）が要る。**
詳細と一覧は設計書 8.2。

```
create_portrait_character(
  image=<南向きスプライトのbase64>,
  direction="character_to_portrait",
  view="low top-down",
  result_size=128)      # 25世代。64デザイン単位の枠にちょうど収まる
```

`image` は base64 しか受け取らずURLが使えない。PowerShell で

```
[Convert]::ToBase64String([IO.File]::ReadAllBytes("...\south.png"))
```

素材はスプライトなので数KBに収まる。

会話に出すには `data/dialogue/*.json` の話者に `"portrait": "<キー>"` を足す。
`src/core/assets.ts` の `portrait.<キー>` と一致させること。

## 7-4. エフェクト・BGM（完了）

エフェクトはCanvas描画で自作（`src/fx/`）。ブルーム・炎上・詠唱演出の3つ。

**曲は Suno で3本作った。** フリー素材は使っていない（当初はPeriTuneを第一候補にしていたが、
第1章と第2章を同じ旋律の変奏にするという条件が、寄せ集めでは満たせなかった）。
7つの場面を3本でまかなう割り当ては `src/core/audio.ts` の `TRACKS`。

**効果音は音声ファイルを持たない。** `src/core/sfx.ts` が WebAudio で合成する。
素材を探す時間もライセンス管理も要らず、音色を1か所で揃えられる。

出典と利用条件は `docs/assets-license.md`。
**Suno の利用条件はプランによって変わるので、公開前に必ず確認すること。**

## 完了条件

矩形が1つも残っていない。

# Phase 8 — シナリオ流し込みとバランス調整

## 8-1. テキストを全部書く

会話文は `data/dialogue/*.json` にある。**書き方の規則は `docs/台本の書き方.md`。**
直したら必ず走らせること。

```bash
npm run lint:script
```

枠からはみ出す行は**ゲーム中で黙って切れる**ので、目では気づけない。

- 第1章の日常会話（ミラの台詞は話しかけるたびに変わる）
- **`MIRA` の露出回数を数える。第1章で最低20回**（設計書 2.3）
- 第2章・第3章のイベントテキスト
- ラスボスの台詞（説明台詞を書かないこと）
- 断章40本

## 8-2. 戦闘バランス

全戦闘が手配置なので、**1戦ずつ手で調整する**。
ただし「MPが足りるか」は計算できる。

```bash
npm run balance
```

章ごとに、**確実に持っている呪文だけで**全戦闘を抜けられるかを見る。
確実に持っている呪文とは、人から教わるか決まった場所で拾えるものだけで、
**打って偶然当てた呪文は数えない。運を前提にしたバランスは調整ではない。**

### 何を見るか

かつては「章のMP消費が9割か」を見ていた。**今は逆を見る。**

> **乱打の余地** … 章を抜けたあと、不発（MP3）を何回ぶん打てるか。**下限 30 回。**

MPを実質のライフバーにしていた頃、通しプレイで
「MPがきつすぎて適当な呪文を打つ余裕がない」という指摘が出た。
**知らない言葉を打ってみることがこのゲームの中心**なので、これは致命的だった。
MPを約3倍にし、緊張はMPではなく**手番**に移してある（設計書 5.0）。

現在の値：第1章 34回 ／ 第2章 63回 ／ 第3章 92回。

**呪文を配る場所を増やしたら必ず回すこと。** 一度、灰の中の声の報酬を
`JAKROS`（NAME 70）にしたところ、ラスボスが2ターンで沈んだ。
必ず手に入る報酬は、**終幕に効かない属性**を選ぶ（設計書 4.7）。

数値を触ったら必ず回すこと。**レベルを廃止して威力が固定になった**ので、
敵のHPと防御はそのまま「何ターンかかるか」になる。
かつての `LEVEL_GAIN` のような、全戦闘に効くつまみはもう無い。

- 総戦闘数 15〜25回、ボス3体
- 敵のHPは「何ターンかかるか」で調整する。MPで縛らない
- LEVELS・ITEM_MP・章ごとの補給は、ツールが
  `src/game/player.ts` と `src/field/state.ts` から**読む**。
  書き写さないこと（一度ずれた）

## 8-2.5 `MIRA` を打てるか確認する

通しプレイの最後、禁書の白紙を前にして、**プレイヤーが `MIRA` と打てるか**を見る。
会話の話者名は「ミラ」（カタカナ）なので、当番表・机の落書き・目録だけが
アルファベット表記の露出経路になっている（設計書 2.3）。

打てないようなら、**話者名をアルファベット表記に切り替える。**
その場合、**司書長にも固有名を与えること。** 一人だけ名前があって
他が役職表記のままだと、そこだけ浮く。

## 8-3. 通しプレイ

**自分で最初から最後まで通す。**

**時計は見ない。** かつてここに「60分を大きく超えるなら削る」と書いてあったが、
その数字は取り下げた（設計書 1.1）。尺は結果であって、判断の根拠ではない。
長さで判断すると、真っ先に削られるのは第1章の日常であり、
そこはこの作品でいちばん削ってはいけない場所である。

見るのは**どこで手が止まったか**、**どこを飛ばしたくなったか**。
退屈な場面があるなら、それは長いからではなく効いていないからである。
削るのではなく、まず効かせられないかを考える。

## 8-4. 他人にテストしてもらう

見るべきは1点：**入力補完なしで未知の文字列を打つ勇気が出るか。**
出ないなら、序盤に「乱打で当たった」体験を1回仕込む。

## 9-2. Cloudflare Workers へデプロイ

GitHubリポジトリを Cloudflare Workers に接続する。
ビルドのルートは `package.json` と `wrangler.jsonc` があるディレクトリにする。

- ビルドコマンド：`npm run build`
- デプロイコマンド：`npx wrangler deploy`
- Worker 名：`funsho-no-yoru-game`（`wrangler.jsonc` の `name` と揃える）

本作はブラウザーで動作する静的なゲームなので、Workers Static Assets で
ビルド済みの `dist`（HTML・JavaScript・画像・音声）を配信する。
公開フォルダーは `wrangler.jsonc` の `assets.directory` に `./dist` と指定する。
サーバー側の Worker スクリプトを実行しないため、`main` は不要。

Pages 専用の `pages_build_output_dir` は使わない。この設定のまま
`wrangler deploy` を実行すると Pages プロジェクトという警告が出て、
Workers 用の `main` も `assets.directory` も見つからず
`Missing entry-point to Worker script or to assets directory` で失敗する。
`npm run build` の成功は `dist` の生成完了を意味し、公開先の設定が正しいことまでは保証しない。

参考：[Cloudflare 公式の Pages から Workers への移行手順](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/)
