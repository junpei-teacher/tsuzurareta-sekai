プログラミング技術 ・ デプロイ編

はじめての git push

Kiro で作ったアプリを GitHub に送り、Cloudflare Workers で公開する手順です。上から順番に進めてください。コマンドは「コピー」を押して、ターミナルに貼り付けて Enter で実行します。

  1. 手順 1GitHub でリポジトリを作る
  2. 手順 2Kiro で準備する
  3. 手順 3〜5コマンドで GitHub に送る
  4. 手順 6Workers で公開する

一度試した人が、新しいリポジトリでやり直すとき

作ったアプリのフォルダーをそのまま使えます。リポジトリを作り直すだけでは、Pages 用設定は変わりません。手順2のプロンプトで Kiro に既存設定も Workers 用に直してもらいます。

  1. 手順1で空のリポジトリを新しく作り、その URL をこのページに貼る。以前の URL が残っていたら貼り替える。
  2. 手順2のページ内プロンプトをコピーして Kiro に送る。新しい Worker 名になっていることを確認する。
  3. 設定の修正と検証後、手順4を進める。既に Git 管理されていても .git を削除する必要はない。git init が Reinitialized と表示されても既存の管理情報を使って進められる。
  4. 4-6 では既に送り先がある人は「やり直す人」のコマンドを使い、新しい URL に変更する。
  5. Cloudflare では新しい Worker を作り、新しいリポジトリを接続する。既存の Pages プロジェクトはそのままでは Worker に切り替わらない。

新しい名前は以前と区別できるもの（例：my-quiz-app-v2）にすると確認しやすくなります。古いリポジトリや公開サイトは、この作業のために削除する必要はありません。チェック済み表示が残っていても、今回は各手順を確認し直してください。

1

GitHub でリポジトリを作る

  1. ブラウザで GitHub を開き、右上の「+」→「New repository」
  2. Repository name は半角の小文字・数字・ハイフン（-）だけで付ける。例：my-quiz-app
  3. Public / Private は先生の指示どおりにする
  4. README・.gitignore・ライセンスは追加しない（初めの状態のまま）で「Create repository」
  5. 次の画面で「HTTPS」を選び、表示された URL をコピーして下に貼る
注意　README などを追加して作ると、手順4の最後で送れなくなります（「困ったとき」の rejected を参照）。

まだ貼られていません。GitHub の画面で HTTPS の URL をコピーして貼ってください。

2

Kiro で準備する

  1. Kiro でアプリのフォルダを開く
  2. 新しいチャットを開き、下の「Kiro 用プロンプト」の「コピー」を押して貼る。別のテキストファイルを開く必要はありません
  3. 1行目の「Worker 名：」の後ろを に書き換えてから送信する。末尾の .git は付けない
  4. Kiro の構成確認を読む。サーバー処理がある場合は対応方針を先生と確認する。静的アプリは設定と検証が終わるまで待つ
  5. Kiro の検証結果と、Worker 名・ビルドコマンド・デプロイコマンド・ルートディレクトリをメモする。未確認・エラーがあれば先生に見せる
なぜ先に Kiro？　公開するフォルダーを Workers に伝えるためです。設定なしでも自動設定される場合はありますが、授業では明示して確認します。静的アプリは assets.directory を使います。pages_build_output_dir は Pages 専用です。

Kiro 用プロンプト

この欄だけで読んでコピーできます。　手順1の URL を入れると Worker 名も入ります。長い文章は欄の中をスクロールして読めます。「コピー」で全文をコピーし、Kiro の新しいチャットに貼ってください。以前 Pages 用に準備したアプリにも使えます。送信前に1行目を確認してください。

6. Cloudflare Workers で公開する

Cloudflare の「Workers & Pages」から作成画面を開き、Worker の Git リポジトリ接続を選びます。「Continue with GitHub」などの表示から、自分のリポジトリを接続してください。画面名は変わる場合があります。

画面を確認　Pages 用の作成画面へ進まないでください。「ビルド出力ディレクトリ」を入力する Pages の手順ではありません。Workers は「デプロイコマンド」に npx wrangler deploy を使い、公開フォルダーは設定ファイルの assets.directory で指定します。

本番ブランチは、この手順で送った main を接続していることを確認します。今回のセットアップ画面にはブランチの入力欄は表示されていません。この表は静的アプリ用です。SSR・API・認証などがある場合は、Kiro が調べた Workers 対応構成を先生と確認して使います。

  1. 設定を確認してデプロイする。
  2. ログでビルドとデプロイの両方が成功したことを確認する。Build command completed だけでは公開完了ではありません。
  3. Cloudflare に表示された公開 URL を開き、画像・音声・ボタンなどを確認する。画面を再読み込みしても動くか確認する。
dist を GitHub に送らなくてよい理由　Vite の場合、Cloudflare がソースからビルドし、その場で dist を作ります。手書きの HTML や素材が入る公開フォルダーは GitHub に送る必要があります。

デプロイで止まったら

最後の「Failed」だけでは原因はわかりません。失敗したコマンドと、最初の ERROR、その前後を Kiro に渡します。トークン・パスワード・秘密の環境変数は貼らないでください。

ログの表示意味・確認すること
Build command completedビルド完了。この後にデプロイが続きます。
Pages projectPages 用設定が残っていないか確認。静的 Workers では pages_build_output_dir を assets.directory に置き換えます。pages deploy に変更しません。
Missing entry-point to Worker script or to assets directoryWorkers が公開対象を見つけていません。静的アプリは assets.directory、サーバー処理がある構成は main や公式アダプターの出力設定を確認します。ブラウザー用 main.ts を指定しません。
公開フォルダーが存在しないビルドコマンド、出力先、ルートディレクトリの組み合わせを確認します。
Worker 名が一致しないCloudflare で選んだ Worker と設定の name を一致させます。
公開後に白い画面・画像が出ないブラウザーのエラーと素材の URL、GitHub に素材があるか確認。公開成功とアプリの正常動作は別々に確認します。

前回のエラーの例：ビルド成功 → Pages 用設定の警告 → Workers 用の公開対象なし → 失敗。原因はビルドではなく、デプロイ設定です。

参考：Pages と Workers の設定の違い ／ Workers Builds の設定

2回目から（アプリを直したとき）

同じリポジトリ・Worker を更新する場合は、手順1〜3と 4-1・4-5・4-6 はもう要りません。新しいリポジトリでやり直す場合は、上の「一度試した人」の手順を使います。直したら、Kiro でビルドと公開しない検証（dry-run）を確認してから、次のコマンドを実行します。コミットは貼り付けたあと、" " の中を「何を直したか」に書き換えてから Enter を押します。

PS C:\…>
PS C:\…>
PS C:\…>

Workers と GitHub の連携が済んでいれば、接続した本番ブランチへのプッシュで Cloudflare が再デプロイします。ログの成功と公開ページの動作を確認してください。

困ったとき

ターミナルに出た英語の中から、下と同じ文を探してください。出てくる順に並んでいます。

  • warning: … LF will be replaced by CRLF …4-2 ・ 心配なし
    原因
    Windows と Mac で改行の書き方が違うのを、git が自動で調整しているお知らせです。
    直し方
    何もしなくて大丈夫です。そのまま次へ進みます。
  • git status に node_modules や .env が出てきた4-3
    原因
    .gitignore がない、または中身が足りません。
    直し方
    Kiro に「.gitignore を直して」と頼みます。直ったら、次の2つを順に実行して候補を入れ直します。
    PS C:\…>
    PS C:\…>
  • Author identity unknown
    *** Please tell me who you are.    4-4
    原因
    「はじめる前に」の設定がまだです。
    直し方
    ページ上の「はじめる前に」を済ませてから、4-4 をもう一度実行します。
  • 黒い画面に切り替わって、戻れない4-4
    原因
    -m "…" を付けずにコミットしたので、メッセージを書く画面（vim）が開きました。
    直し方
    入力を半角にしてから Esc を押し、:q! と打って Enter。元の画面に戻ったら、4-4 をコピーしてやり直します。
  • error: remote origin already exists.4-6
    原因
    送り先はもう登録されています（4-6 を2回実行した、など）。
    直し方
    次のコマンドで、送り先を手順1の URL に上書きします。
    PS C:\…>
  • error: src refspec main does not match any4-7
    原因
    コミットができていません。
    直し方
    4-2（git add .）と 4-4（git commit）をやり直してから、4-5 → 4-7 と進みます。
  • ! [rejected] main -> main (fetch first)4-7
    原因
    手順1でリポジトリを作るときに、README などを追加しました。
    直し方
    作ったばかりのリポジトリのときだけ、次のコマンドで上書きして送れます。それ以外のときには使いません。
    PS C:\…>
  • remote: Repository not found.4-7
    原因
    URL が間違っているか、ブラウザで別の GitHub アカウントにログインしています。
    直し方
    手順1の URL を GitHub の画面と見比べ、違っていたら貼り直して「remote origin already exists」の直し方で上書きします。それでも出るときは先生を呼んでください。
