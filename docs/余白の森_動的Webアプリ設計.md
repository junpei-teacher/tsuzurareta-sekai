# 『余白の森』動的Webアプリ設計

> 対象：Cloudflare Workersを用いる授業用オンライン拡張  
> 状態：方針採用／本編優先で段階導入  
> 更新日：2026-08-26

## 0. この文書の役割

本書は『余白の森』を、単体で完結するブラウザゲームから、授業で段階的に育てられる動的Webアプリへ拡張する契約を定める。
物語、戦闘、固定画面サイドビューの正本は `docs/余白の森_設計書.md` とし、本書はそれらを変更しない。

オンライン機能は本編の完成条件ではない。ネットワーク障害や授業用サービスの停止時にも、プロローグから単一エンディングまで遊べる状態を維持する。

## 1. 採用する体験

### 1.1 中核機能

1. **クラウドセーブ**
   - 別端末から同じ進行を再開できる。
   - 既存のProfileSaveとRunSaveをそのまま教材に使う。
   - localStorageを一次保存とし、通信は後追いで同期する。
2. **教員用進捗画面**
   - 章、最終プレイ日時、発見語数、クリア状況、詰まりやすい地点を確認する。
   - 順位付けではなく、支援が必要な地点を知るために使う。
3. **行商人の動的依頼**
   - 教員がクラス単位で追加依頼、期間、ヒントを配信する。
   - 正史の会話や進行フラグを上書きしない、任意の寄り道とする。

### 1.2 本作固有の目玉

**クラス共同の村復興**を採用する。

- 生徒の依頼達成、言葉の発見、森からの帰還を匿名集計する。
- 一定値で村の灯り、修繕、品物、NPCの短い台詞が増える。
- 個人順位、最速記録、未達者名は表示しない。
- 復興度は正史エンディングの分岐条件にしない。
- 復興による見た目の差はオンライン状態から再生成でき、RunSaveへ不可逆に混ぜない。

### 1.3 発展機能

**森の異変・リアルタイム協力戦**は授業の発展課題とする。

- クラスごとに一つの共有戦闘状態を持つ。
- WebSocketとDurable Objectsで参加者、魔物の状態、貢献を同期する。
- 通常戦闘やラスボス戦の代わりにはしない。
- 切断、再接続、同時更新、荒らし対策まで教えられる時だけ実装する。

R2を使う生徒投稿や画像アップロードは、個人情報、著作権、モデレーションの授業設計ができるまで採用しない。

## 2. 技術構成

```text
ブラウザ（Vite／Canvasゲーム）
  ├─ localStorage              常に使える一次保存
  ├─ /api/session              匿名の授業用セッション
  ├─ /api/save                 クラウドセーブ
  ├─ /api/progress             許可した進捗イベントだけ送信
  ├─ /api/assignments          行商人の追加依頼
  └─ /api/village              クラス共同復興の表示値
             │
Cloudflare Worker
  ├─ 静的アセット配信
  ├─ API、入力検証、認可
  ├─ D1                        セーブ、進捗、依頼、復興度
  ├─ KV                        更新の少ない公開設定（必要になった時だけ）
  ├─ Cron Trigger              日替わり課題（発展）
  └─ Durable Objects/WebSocket リアルタイム協力戦（発展）
```

ViteとCanvas描画を維持し、SSRやフロントエンドフレームワークへの移行は行わない。
静的アセットと `/api/*` を一つのWorkerから配信する。最初はD1だけで実装し、KVやDurable Objectsは用途が発生してから追加する。

## 3. オフライン優先契約

### 3.1 保存順序

1. 現在のProfileSave／RunSave検証を通す。
2. localStorageへ保存する。
3. 画面を止めず、オンライン同期キューへ積む。
4. 同期成功後にserverRevisionとsyncedAtだけを端末へ記録する。
5. 失敗時は進行を止めず、「端末には保存済み／クラウド同期待ち」と区別して示す。

「サーバーへ保存できなかったためゲーム自体を続けられない」設計は禁止する。

### 3.2 競合

- RunSaveは自動でフィールド単位に合成しない。章や位置を混ぜると進行不能になり得る。
- サーバーと端末の双方に新しいRunSaveがある場合、日時、章、目的を見せてプレイヤーに選ばせる。
- ProfileSaveのdiscoveredWordsは集合として統合できる。
- clearedは一度trueになったらfalseへ戻さない。
- 書き込みにはclientMutationIdを付け、再送で二重計上しない。

### 3.3 正史との分離

- オンライン依頼はstory flagsと別のonline flagsへ保存する。
- 共同復興度は村の追加装飾と任意会話だけを変える。
- SLANE、SENA、セナとの和解、名留めの環、単一EDはサーバーデータで変更しない。
- 教員画面から本編の答えや最終入力を一斉配信する機能は作らない。

## 4. データと個人情報

### 4.1 生徒の識別

- クラスコードは教室の選択に使うが、認証秘密として扱わない。
- 初回参加時にランダムなstudentIdと再開用トークンを発行する。
- ゲーム内主人公名はクラウドへ送らない。画面上の名前と教員名簿を自動で結び付けない。
- 教員が必要な場合だけ、管理画面側でstudentIdへ教室内の呼称を付ける。
- 実名、メールアドレス、自由記述、キー入力履歴は初期版で収集しない。

### 4.2 送信してよい進捗

- 章番号とパネルID
- 発見語の数。内容そのものはクラウドセーブ以外の集計へ複製しない
- 戦闘開始、勝利、敗北、ヒント利用を表す定義済みイベント
- 依頼の達成
- クリア状態
- サーバー受信時刻

会話本文、入力途中の文字、任意の自由文を分析用イベントに含めない。

### 4.3 D1の初期テーブル

| テーブル | 役割 |
|---|---|
| classes | クラスと表示設定 |
| students | 匿名studentId、クラス、無効化状態 |
| save_slots | ProfileSave、RunSave、revision、更新時刻 |
| progress_events | 定義済みイベント。eventIdで重複排除 |
| assignments | 行商人の追加依頼と公開期間 |
| assignment_results | 生徒ごとの達成。重複報酬を防止 |
| village_state | クラスごとの復興度と表示段階 |

JSON保存だけで始めてもよいが、章、更新時刻、クリア状態は教員画面で集計できる列として持つ。

## 5. API契約

すべてのAPIはJSONを返し、成功時にも `schemaVersion` を含める。未知のフィールドは読み飛ばせても、未知のschemaVersionを黙って保存しない。

| Method | Path | 役割 |
|---|---|---|
| GET | /api/health | 配信とWorker実行の確認 |
| POST | /api/session/join | クラスへ匿名参加 |
| GET | /api/save | 最新のクラウドセーブ取得 |
| PUT | /api/save | revision付きセーブ更新 |
| POST | /api/progress | 許可リスト方式の進捗イベント送信 |
| GET | /api/assignments | 現在公開中の追加依頼取得 |
| POST | /api/assignments/:id/complete | 達成と報酬の一度だけの確定 |
| GET | /api/village | 復興度と見た目段階の取得 |
| GET | /api/teacher/overview | 教員用の匿名集計 |

初期実装は `/api/health` だけから始め、認証なしでセーブAPIを公開しない。

## 6. 教員画面

### 6.1 表示するもの

- クラス全体の参加人数、章別人数、クリア人数
- 生徒IDごとの現在章、最終同期、発見語数
- パネルまたは戦闘単位の敗北・ヒント利用集計
- 未同期が長い端末があること。ただしオフラインを未学習と断定しない
- 追加依頼の作成、公開停止、対象クラス指定
- 村復興の現在段階

### 6.2 表示しないもの

- 入力速度ランキング
- 常時監視に見えるリアルタイム操作履歴
- 入力途中の文字列
- 本人が送っていない端末情報
- 公開URLから閲覧できる個人別進捗

教員画面は生徒用APIと認可を分ける。集計画面を実装する前に、教員本人を確認できる認証方式を用意する。

## 7. 導入工程

| 工程 | 実施時期 | 内容 | 完了条件 |
|---|---|---|---|
| W0 | 現在 | 本書、API境界、オフライン契約を確定 | 本編設計と矛盾しない |
| W1 | Phase 5完了後 | Workers静的配信と `/api/health` | ローカルとプレビューで同じゲームが動く |
| W2 | Phase 7完了後 | D1、匿名参加、クラウドセーブ、教員進捗 | 別端末再開、競合選択、権限検査が通る |
| W3 | Phase 9の物語確定後 | 行商人の動的依頼、共同復興 | オフライン本編と単一EDに影響しない |
| W4 | 本編公開後の発展 | 日替わり試練、Durable Objects協力戦 | 切断復帰と同時更新を授業で検証できる |

W1以降はWranglerのlocal／preview／production環境を分ける。授業中に本番DBを直接編集しない。

## 8. 各工程で学ぶ内容

| 工程 | 主な学習内容 |
|---|---|
| W1 | HTTP、ルーティング、環境差、デプロイ |
| W2 | REST、JSON、SQL、マイグレーション、検証、認証、競合 |
| W3 | CRUD、管理画面、集計、冪等性、プライバシー |
| W4 | 定期実行、WebSocket、共有状態、切断復帰、同時実行 |

機能を見せることより、生徒が「なぜブラウザだけでは実現できないか」を説明できることを各工程の到達点とする。

## 9. やらないこと

- 本編完成前にオンライン専用の巨大機能を作る。
- ネット接続をゲーム開始条件にする。
- クラスコードだけで教員権限を与える。
- クライアントが送った復興ポイントやクリア判定を無検証で信用する。
- セーブの更新競合を最終書き込みだけで黙って上書きする。
- 学習目的の説明なしに複数のCloudflareストレージを導入する。
- 本番データを使ってデータベース操作の授業を行う。
